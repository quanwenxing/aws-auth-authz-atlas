AWS上の認証・認可を、迷子にならずに理解する。

IAM、IAM Identity Center、Cognito、OAuth 2.0、OpenID Connect、SAML、フェデレーション、STS まで。 「誰なのかを確かめる話」と「何をしてよいかを決める話」を分けて、AWSでどう組み合わせるかを網羅的に整理した資料です。

まず一言でいうと

認証（Authentication）は「あなたは誰？」、認可（Authorization）は「何をしていい？」。

AWS実務では、この2つを分離して考えると一気に理解しやすくなる。たとえば、Googleでログインするのは認証、その後にS3を読めるか・Lambdaを実行できるかを決めるのは認可。

認証 = Identity 認可 = Permission AWSでは STS が橋渡し Webアプリでは OAuth/OIDC が重要
IAMAWS内部の権限制御の中核
Identity Center社員向けSSOの本命
Cognito顧客向けログイン基盤
STS一時クレデンシャル発行役
Overview

全体像はこの4層で見る。

AWSの認証認可は、単一サービスで全部やるより、役割分担で理解すると整理しやすい。 「IdPで本人確認 → AWSが一時権限を払い出す → IAMで許可判定 → アプリ/APIが受け入れる」の流れが基本。
Layer 1 Identity Provider Google / Microsoft Entra ID / Okta / IAM Identity Center / Cognito User Pool
→
Layer 2 Token / Federation OAuth 2.0 / OIDC / SAML / JWT / Federation
→
Layer 3 AWS Credential Bridge STS / AssumeRole / AssumeRoleWithSAML / AssumeRoleWithWebIdentity
→
Layer 4 AWS Authorization IAM Policy / Resource Policy / SCP / Permission Boundary / ABAC
→

Basics

基礎知識：まずは言葉を混ぜない。

初学者が混乱しやすいのは、ログインの仕組み、トークン、AWS権限、SSOが全部ごちゃ混ぜになること。 ここでは似た言葉を分けて整理する。

認証

本人確認。ID/パスワード、MFA、Googleログイン、社員ディレクトリ連携など。

例：Cognito User Pool、Entra ID、Okta、IAM Identity Center

認可

認証後に、どこまで許可するか決めること。AWSではIAMポリシーが中心。

例：S3 readのみ、DynamoDB write不可、特定アカウントのみ入室可

SSO

一度ログインすると複数アプリに再ログインなしで入れる体験。仕組みそのものではなく、体験の名前。

裏側では OIDC / SAML / Cookie / Session などを使う

OAuth 2.0

第三者アプリが、ユーザーの代わりに限定されたアクセスを得るための認可フレームワーク。重要なのは「OAuth自体はログイン規格ではない」こと。

  • Access Token を発行して API にアクセスさせる
  • Authorization Code + PKCE が現代Web/SPA/モバイルの基本
  • Client Credentials はサーバー間通信向け

OpenID Connect (OIDC)

OAuth 2.0 の上に載る「認証」のレイヤー。ユーザーが誰かを示す ID Token を定義する。

  • OAuth = APIアクセスの許可
  • OIDC = ユーザーの身元確認 + プロフィール情報の受け渡し
  • 多くの「Googleでログイン」は OIDC ベース

SAML 2.0

企業SSOでよく使われてきたXMLベースのフェデレーション標準。古参だが今も社内SSOで強い。

JWT

トークンの表現形式。OIDCのID TokenやOAuthのAccess Tokenで使われることが多いが、JWTそのものは規格名ではなくフォーマット。

フェデレーション

外部の認証基盤を信頼して、自分のシステムに入れること。AWSでは「外部IdPを信じて一時権限を出す」が本質。

OAuth / OIDC

OAuth 2.0 と OIDC の仕組みを一度で掴む。

「Access Token」「Refresh Token」「ID Token」「Authorization Server」が並ぶと一気に難しく見えるけど、やっていることはシンプル。
1
ユーザーがログイン画面へ移動
アプリは認証サーバーへリダイレクトする。ここでユーザーがGoogleやCognitoにログイン。
2
認証サーバーが許可を確認
「このアプリにこの範囲のアクセスを許可していい？」を確認。OAuth的には consent。
3
認可コードを返す
Authorization Code Flow では、いきなりトークンではなく短命の code を返す。
4
アプリがトークン交換
バックエンドまたはPKCE付きクライアントが code を token endpoint に送り、Access Token / ID Token / Refresh Token を受け取る。
5
APIアクセス or ユーザー識別
Access Token は API用、ID Token は「誰がログインしたか」確認用。Refresh Token は再ログインなし更新用。

トークンの役割

トークン役割使う相手注意
Access TokenAPI利用の権限を示すResource Server / APIクライアントで中身を決め打ちしない
ID Tokenログインしたユーザー情報を示すClient / AppAPI認可の代用にしない
Refresh Token新しいトークンを再取得Authorization Server漏えい時の影響が大きいので厳格保管

PKCE

SPAやモバイルで Authorization Code Flow を安全に使うための補強。今は「使うのが普通」と考えてよい。

Scopes / Claims

Scope は欲しい権限の範囲、Claim はユーザー属性。OIDCでは openid profile email などが代表例。

AWS Services

AWSの主要サービスを役割で理解する。

名前が似ていても、対象ユーザーが違う。社員向けなのか、顧客向けなのか、機械向けなのかで選び分ける。

IAM

AWSリソースに対する認可の中核。ユーザー、ロール、ポリシー、リソースポリシーなどで「何ができるか」を決める。

  • User: 長期認証情報を持つ人/アプリ用主体。ただし現代実務では多用しない
  • Role: 一時的に引き受ける権限の箱。人にも機械にも使う。実務の主役
  • Policy: JSONで許可/拒否を書く
  • Resource-based Policy: S3 bucket policy, Lambda permission など

STS

Security Token Service。一時的なAWS認証情報を発行する。外部IdPとAWS権限をつなぐ橋。

AssumeRole / AssumeRoleWithSAML / AssumeRoleWithWebIdentity

IAM Identity Center（旧 AWS SSO）

社員・社内委託先など workforce identity 向けのSSO基盤。複数AWSアカウントやAWSアプリへのアクセスを一元管理する。

  • 旧称 AWS Single Sign-On
  • 外部IdP（Entra ID / Okta等）や社内ディレクトリ連携ができる
  • AWS Organizations と組み合わせて複数アカウント権限を集中管理しやすい

Amazon Cognito

顧客向け（B2C / CIAM寄り）のログイン基盤。Webやモバイルアプリのサインアップ/サインインに使う。

  • User Pools: ユーザーディレクトリ + 認証サーバー。OIDC / OAuth 2.0 の発行者になれる
  • Identity Pools: 外部で認証済みのユーザーに、AWS一時クレデンシャルを払い出す
  • Google / Apple / Facebook / SAML / OIDC などと連携可能

AWS Organizations / SCP

各アカウントの上位ガードレール。SCP は「最大許可枠」を制限する。Identity Centerと相性がいい。

Permission Boundary

IAM主体に付ける上限枠。委任管理やセルフサービス作成時の暴走防止に使う。

Session Policy

AssumeRole 時に、さらにそのセッションだけ絞る追加制約。短期的な最小権限化に便利。

ABAC / RBAC

RBAC は役割ベース、ABAC は属性ベース。AWSではタグや属性を使ってABACを組むと大規模運用に強い。

AWS Directory Service

Microsoft AD などのディレクトリ連携を扱う周辺サービス。社内認証基盤やWindows系統合と絡む場面で登場する。

IAM Roles Anywhere

AWS外部のサーバーやオンプレ機器に、証明書ベースで一時AWS認証情報を配る仕組み。外部ワークロード向け。

Amazon Verified Permissions

アプリ独自の細かい認可判定を外出ししたい時の選択肢。AWSリソース権限ではなく、アプリ内認可に向く。

Patterns

実務ではどう組み合わせるか。

ここが一番大事。理屈だけでなく、「誰向けのシステムか」で部品の選び方が変わる。

① 社員が複数AWSアカウントへ入る

推奨構成: 外部IdP（Entra ID / Okta） ↔ IAM Identity Center ↔ Permission Set ↔ 各AWSアカウントのRole

  • 社員はSSOポータルからログイン
  • AWS Organizations配下の複数アカウントへ一元付与
  • 権限設計は job function ごとに Permission Set 化
  • SCPで全体ガードレールを敷く

② 顧客がWebアプリにログインする

推奨構成: Cognito User Pool ↔ アプリ ↔ API Gateway / ALB / バックエンド

  • ユーザー登録、ログイン、MFA、パスワードリセットをCognitoに寄せる
  • アプリは OIDC / OAuth 2.0 でトークンを取得
  • API側は JWT authorizer / Cognito authorizer で検証

③ 顧客アプリからS3等へ直接アクセスさせたい

推奨構成: Cognito User Pool or 外部IdP → Cognito Identity Pool → STS → 一時AWSクレデンシャル

  • 「ログイン」はUser Pool、「AWS資格情報払い出し」はIdentity Poolで役割分担
  • 未ログインの匿名ゲストにも限定権限を配る設計が可能

④ GitHub Actions からAWSへ安全にデプロイ

推奨構成: GitHub OIDC → IAM OIDC Provider → AssumeRoleWithWebIdentity → STS一時権限

  • 長期AWS Access KeyをGitHub Secretsに置かなくてよい
  • sub / aud 条件で repository・branch・environment を厳密制限

⑤ B2B SaaSで企業のIdPと連携して社員ログインさせたい

推奨構成: 顧客企業IdP（SAML or OIDC） ↔ Cognito User Pool（federation） ↔ アプリ

  • 自社で認証情報を持たず、相手企業のEntra ID/Oktaを信頼
  • アプリ側では最終的に自分のUser Poolトークンで統一処理しやすい

⑥ AWSサービス間・EC2/Lambda/ECS の権限

推奨構成: IAM Role を各実行環境に付与

  • EC2 Instance Profile、Lambda Execution Role、ECS Task Role を使う
  • Access Key直書きは避ける
  • 最小権限、短命資格情報、CloudTrail監査が基本

⑦ APIを保護したい

推奨構成: Cognito / 外部OIDC の JWT を API Gateway Authorizer や ALB 認証機能で検証

  • フロントはOIDCでログインし Access Token を取得
  • API Gateway は JWT authorizer / Cognito authorizer を利用
  • ALB でも authenticate-oidc / authenticate-cognito が使える
Design Rules

実務でよくある勘違い。

このへんを踏み外すと、設計が危うくなる。

OAuth = ログイン、ではない

OAuth 2.0 は認可。ログインまで含めたいなら OIDC を見る。

ID Token でAPI認可しない

ID Token は「誰か」の情報。API認可は Access Token やIAM側で判定する。

IAM User を増やしすぎない

人も機械も、長期キーよりロール + 一時資格情報が原則。

Cognito と Identity Center を混同しない

ざっくり、顧客向けは Cognito、社員向けは Identity Center。

SCP は許可付与ではない

SCPは上限枠。IAMポリシーで許可されていても、SCPで止まる。

フェデレーション後もIAM設計は必要

外部IdPで本人確認できても、AWS内で何を許可するかは別問題。

Summary

迷ったら、この判断基準。

サービス選定を短く言うとこうなる。

社員のAWSアクセス

IAM Identity Center を第一候補にする。

顧客のアプリログイン

Cognito User Pools を第一候補にする。

外部CI/CDや外部IdPからAWS権限取得

OIDC/SAML federation + STS + IAM Role。

権限の本体

最後は常に IAM で絞る。
